# 踩过的坑（现象 → 原因 → 修法）

## 1. 日期整体错一天（凌晨 0~8 点）

**现象**：问「今天有什么活动」返回昨天的；月末上传的文件落到上个月目录。
**原因**：容器时区是 UTC（`TZ` 为空），MySQL 是 CST。`datetime.now()` 在 CST 00:00~08:00 取到的是「昨天」。
**修法**：所有取时间都走 `app/common/clock.py`（显式 `ZoneInfo("Asia/Shanghai")`、缺 tzdata 时降级固定 +08:00）；compose 传 `TZ` 只是让日志时间戳对齐，**正确性不依赖它**。

## 2. 往 `text` 里加一个字段，账单一夜翻倍

**现象**：只加了一行「开始时间：…」，重建索引花掉几百次 embedding。
**原因**：指纹是 `sha1(text)[:16]`，`text` 变一个字符 → 指纹变 → 全部重算。
**修法**：元数据（时间、页码、类型）一律放结构化字段，不拼进 `text`。时间过滤靠 `where` 谓词，不靠向量。

## 3. 检索结果「答非所问」，但不报错

**现象**：分数正常、结果正常返回，只是答案对不上问题。
**原因**：`vectors.npy` 与 `docs.json` 靠**行号**对齐，没有 id 可反查。两次 `os.replace` 之间崩溃（或手工改过其中一个文件）就会出现「新向量 + 旧文档」，行数相同则校验也发现不了。
**修法**：只通过 `ingest` 改索引；`index.py` 加载时校验行数一致；现阶段别手工编辑 `data/rag/*`。数据量大到需要版本戳时再引入 manifest。

## 4. 上传的 PDF 切出 63 块，其中 86% 是标签

**现象**：一份一页的成绩单，解析出 20149 字、63 块，问答命中率低。
**原因**：MinerU 对合并单元格表格输出内联 HTML（`<td rowspan=1 colspan=1>`），按 400 字硬切会把标签切断（`… | 创新创` + `修 | 36(学时)`）。
**修法**：`normalize_markdown` 把 HTML 表格转成 pipe 行、每行独立成段，再切块。实测 25233 字 → 3872 字、63 块 → 15 块。
**注意**：**已经入库的坏块修不回来**（切痕已固化），必须重传一次。

## 5. 旧索引让时间过滤静默失效

**现象**：代码加了时间窗，线上却仍返回所有活动；不报错、不丢数据。
**原因**：`docs.json` 是旧版本，没有 `start_time` 字段 → `parse_dt(None)` 放行。
**修法**：改完索引结构必须重跑 `python -m app.rag.ingest --limit 0`（指纹命中，**0 次 embedding**）。索引没有 `schema_version`，新代码跑旧索引永远静默降级。

## 6. 工具报错被「降级」掩盖

**现象**：接口 200，回答是「这次查询没成功」；日志里才有一行 `工具执行失败`。
**原因**：改 `_time_filter` 函数体时漏改了函数签名（`time_range, now` → 需要第三个参数），`py_compile` 不检查参数个数，上线才炸。
**修法**：改函数签名后 `grep` 全仓调用点；工具改动必须端到端跑一次真实请求，不能只看 import 通过。

## 7. 镜像构建失败：lock 与 pyproject 不一致

**现象**：`docker compose build` 在 `uv sync --frozen` 处退出。
**原因**：`pyproject.toml` 加了依赖，但只 `uv pip install` 装进了本地 venv，没 `uv lock`。
**修法**：改依赖后必须 `uv lock` 并一起提交；`.venv` 里的包不代表 lock 里有。

## 8. 附件正文跟着历史每轮重发

**现象**：长会话 token 越来越高，摘要质量还变差。
**原因**：附件块被拼进 `HumanMessage`，随 checkpointer 永久保留，之后每一轮都重发约 1000 token，摘要还要咀嚼一遍。
**修法**：`HumanMessage` 只存用户原话；附件块在 `agent` 节点临时拼到**消息副本**，不落状态；追问靠 `doc_urls` 重新检索（每轮多一次 query embedding，净省约 700 token）。

## 9. 并发同会话，历史被静默覆盖

**现象**：两个标签页同时发消息，其中一个的回复在历史里消失了。
**原因**：checkpointer 是 last-write-wins，两个请求各自读旧状态、写回时后写覆盖先写。
**修法**：`app/agent/locks.py` 按 `thread_id` 加锁串行，同一会话的第二个请求排队。锁按事件循环惰性创建，不能写成模块级 `asyncio.Lock`（换 loop 会永久挂起）。

## 10. 线上跑的是旧代码

**现象**：源码已改，线上行为没变（例如 `status = 1` 与 `status IN (1,2)` 的差别）。
**原因**：服务器上有一份独立代码副本，同步时漏文件；或改了没重新 build。
**修法**：部署只认一条链路（源码 → `docker compose build agent` → `up -d`），不要直接进容器改文件；验收时进容器 `python -c "import ..."` 确认行为，而不只是看 `docker ps`。

## 改动前自检

- 改的是 `text` 里的内容吗？→ 会全量重算向量
- 改了函数签名吗？→ `grep` 调用点，别只 `py_compile`
- 加了依赖吗？→ `uv lock` 并提交
- 动了索引结构吗？→ 重跑 `ingest`，否则新功能静默不生效
- 动了 env 键吗？→ 同步 `.env.example`
- 涉及外部计费（embedding / chat / 视觉）吗？→ 先问再跑，说明调用次数
